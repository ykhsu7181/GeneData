# ADR-004：新数据仓库空库启用与旧生产系统离线收口

## 状态

Accepted，2026-11-25。

本 ADR 已批准数据层重新开库、旧系统离线收口和继续基于 GeneData 建设的稳定方向。批准不授权关闭旧系统、删除旧表、创建生产新库、部署、回填或修改生产数据；这些操作仍须按本文 Gate 独立评审和验收。

G0 决策收口已于 2026-11-25 完成：重新定位说明成为 active 总体入口，旧总体设计标记为 superseded，ADR-001 至 ADR-003 的迁移实施段落和活动文档索引已同步标注。

2026-11-25 文件归档边界修订：旧数据库仍须形成独立备份并完成恢复验证；旧 `manual_files` 不制作完整独立副本，而是在原位置停止写入、登记清单并作为按需重新接收的历史来源。项目接受该目录作为单份源数据可能无法恢复的风险，不能把清单登记描述为文件内容备份或恢复保证。

## 1. 背景

ADR-001 至 ADR-003 已确定 `DataAsset` 统一科研数据身份、最小文件成员结构以及核心载荷和专业上下文边界。现有开发工作还形成了 T0、T1 和 T4 只读审计与候选分析能力。

生产只读证据同时表明，旧业务数据无法安全地作为新仓初始化数据：

- `Dataset` 同时承担身份、类型、文件集合、科研上下文、权限和描述等多种职责；
- 一个 `Dataset` 不等于一个真实 `DataAsset`；
- 部分记录只有描述，没有可确认的核心文件；
- `DataFile` 记录、物理文件清单和历史 `FileRelation` 不能直接组成可信资产关系；
- 项目、权限和专业实体关系继承了旧系统语义，批量复制会把不确定性带入新仓；
- 继续扩大自动候选和冲突修复规则，会增加迁移专用代码和长期维护成本。

项目需要决定：是继续修复并迁移整个旧数据层，还是保留合理的通用设计与代码，同时让新仓的数据层从空库独立开始。

项目负责人确认，截至 2026-11-25，旧系统没有其他实际用户，仅由本人进行测试，因此不需要维持长期在线的历史查询服务。

## 2. 决策

### 2.1 新仓从空业务库启用

新数据仓库确定继续基于 GeneData 建设，使用独立数据库和独立文件存储。通过正式 migration 创建 schema，通过受版本控制的初始化过程建立必要系统配置，但初始不包含旧生产环境中的科研业务记录和关系。openBIS、Kadi4Mat 和其他平台仅作为设计参考，不再作为本阶段实施前置条件。

不迁移的范围包括但不限于：

- `Dataset` 和 `DatasetAccession`；
- 旧 `DataFile` 数据库记录及其路径登记；
- `FileRelation`；
- 旧 Project、Accession、Sample、Assembly、Annotation 等业务记录；
- 上述对象之间的关系；
- 历史项目成员、数据权限、发布状态和 Manifest 关系；
- T4 生成的候选资产、候选文件成员和候选上下文。

新仓最终 schema 不保留 `Dataset`、`DatasetAccession`、`FileRelation` 等只服务于旧业务体系的活动表。历史 migration 不得修改；在完成模型、命令、API、测试和前端调用审计后，通过新的正向 migration 删除旧结构。新的开发数据库从头执行完整 migration 链时，最终 schema 必须与当前模型和新仓边界一致。

### 2.2 新仓初始化边界

新仓初始化分为：

1. **数据库结构**：由版本化 migration 创建，不读取生产数据库、旧文件或网络资源；
2. **系统配置**：最小 DataType/Profile、文件角色、metadata schema、状态和权限规则随代码版本管理并接受校验；
3. **部署配置**：数据库、存储、密钥、域名、日志和备份位置由环境或部署系统提供，不提交明文密钥；
4. **首批业务记录**：首个系统管理账号、数据治理角色、组织或课题组、Project 和验证用 DataAsset 通过明确的人工步骤或受控命令创建。

不从旧数据库复制用户业务关系、组织、Project、类型配置、权限或基础词表。真实用户、项目和科研数据不得通过 schema migration 自动创建。初始化命令如有必要，必须幂等、可审计并复用唯一业务 service。

### 2.3 新旧系统完全隔离

新仓不得：

- 直接写入旧数据库或旧文件目录；
- 把 `manual_files` 中的旧路径直接登记为活动 `DataFile` 的存储位置；
- 通过符号链接、硬链接或目录映射让新仓直接使用旧文件；
- 建立跨库外键或以旧主键作为新仓身份；
- 自动复制、持续同步或双写旧业务数据；
- 在新仓查询失败时 fallback 到旧关系；
- 让旧系统和新仓同时成为新业务的活动事实来源。

旧系统完成离线收口后停止在线服务，不保留长期运行的前端、后端或数据库查询入口。确需查询旧元数据时，只允许在隔离环境临时恢复旧数据库。新仓启用后，新科研数据只能按新仓规则登记。

### 2.4 旧生产系统离线收口

旧数据库、旧文件目录、对应应用版本和运行证据属于同一历史系统，但采用不同的保全方式：

1. 旧数据库制作完整备份与结构备份，在独立存储保存，并在隔离环境完成数据库恢复验证；
2. `manual_files` 原地保留，不制作完整独立副本；生成包含相对路径、大小和修改时间的全量清单，已有校验值一并登记，实际重新接收时再对源文件计算并核验校验值；
3. 停止旧应用对 `manual_files` 的写入、重命名和删除，不把该目录作为新仓存储目录；
4. 登记应用版本、migration 状态和不含密钥的运行说明；
5. 记录数据库、文件清单、代码和 migration 的统一截止时间；
6. 登记数据库备份位置和保留策略，以及 `manual_files` 的保管位置、负责人和访问控制。

`manual_files` 清单只能证明截止时间点观察到的路径和文件属性，不是文件内容备份。由于不保存完整独立副本，文件被误删、覆盖、损坏或所在存储不可用时可能无法恢复；项目明确接受这一风险。旧数据库恢复成功也不代表旧文件内容可恢复。

数据库恢复验证、文件清单登记和停止写入确认完成后，停止旧前端、后端、定时任务和对外端口，撤销或禁用旧应用的数据库连接。不得直接停止可能承载其他业务的共享数据库实例；只有确认实例专用于旧系统并获得独立批准后，才可停止实例。旧数据库备份、原地保留的文件目录、代码版本与运行说明作为离线历史材料保留，不设置长期在线只读观察期。

旧系统仍需处理安全漏洞、数据损坏、备份失败和未审计写入等风险；不再为迁移目的持续修复旧类型、文件归属或专业关系语义。

文件清单和运行登记是运维与审计证据，不导入新仓业务表。

### 2.5 旧数据只能按新规则重新接收

未来需要使用某份旧数据时，将其视为待重新接收的外部历史数据：

1. 优先从 `manual_files` 清单定位原地保留的真实文件；确需旧元数据时，才在隔离环境临时恢复旧数据库；
2. 计算并核验源文件校验值，确认内容、科研含义和访问授权；
3. 按新仓规则确定 DataType、Profile、核心与辅助文件、项目、权限和科研上下文；
4. 将文件复制到新仓独立存储，不直接引用、链接或移动旧文件；
5. 重新计算目标文件校验值，确认与源文件一致；
6. 创建新的 `DataFile`、`DataAsset` 和关系；
7. 记录最小旧系统来源引用和接收审计。来源引用使用旧系统内的相对标识，不通过公开接口暴露服务器绝对路径。

只有在源文件仍然存在且校验通过时才能重新接收。重新接收不是迁移，不批量导入，不复制旧关系，不保留旧主键语义，也不形成持续同步。

### 2.6 保留合理通用代码，不保留迁移前提

重新开库是数据层决策，不等于重新编写整个应用。现有通用模型、migration、服务和测试只有在以下条件同时满足时才继续使用：

- 能够从空数据库通过正式 migration 建立；
- 不需要旧业务数据才能创建和使用新记录；
- 不形成第二份物理文件或科研数据事实来源；
- 符合 ADR-001 至 ADR-003 仍然有效的模型边界；
- 具有对应测试且没有隐藏的旧关系 fallback。

T0、T1 和 T4 报告作为决策证据保留。只服务于全量候选、回填、双写或旧关系兼容的实现停止扩展；其删除必须先完成调用面、migration 和测试审计，不修改已执行的历史 migration。

### 2.7 终止原全量迁移路线

本 ADR 批准后：

- 终止 T4 的全量回填准备和冲突归零目标；
- 取消原 T5 新旧数据一致性切换；
- 取消原 T6 在迁移完成后退役 `Dataset` 的路线；
- 以“旧数据库独立备份恢复、旧文件原地清单保留、旧应用停止在线服务”替代上述生产迁移目标；
- 不再生成用于自动迁移旧业务关系的新规则或新兼容代码。

T0、T1 和已完成的 T4 只读证据继续保留，不把未迁移描述成数据丢失或迁移失败。

### 2.8 前端影响暂缓实施

本 ADR 不批准前端页面、路由或 API 开发。当前只确认：

- 未来新前端应以 `DataAsset` 为科研数据身份；
- 旧系统停止在线服务并作为离线档案保留；
- 新前端不得依赖旧业务关系、双写或 fallback；
- 前端用户流程和所需后端能力在空库启动及最小后端流程验证后、正式 API 设计前单独规划。

## 3. 对既有决策的影响

本 ADR 不推翻 ADR-001 至 ADR-003 中以下稳定边界：

- `DataAsset` 是新仓的统一科研数据身份；
- `DataFile` 是新仓的物理文件事实来源；
- `AssetFileMembership` 表达资产文件组成；
- 专业实体是可选科研上下文；
- 正式资产需要符合 Profile 的真实核心载荷要求；
- 禁止长期双读、双写和第二套事实来源。

本 ADR 若获批准，将替代这些文档中关于旧生产业务数据映射、回填、一致性切换和迁移后退役的实施路线。批准时必须逐项修订受影响文档和 `docs/ACTIVE_DOCUMENTS.md`，不能仅依赖本段产生隐式覆盖。

## 4. 实施顺序

本 ADR 获批后按以下 Gate 依次实施，每一阶段独立评审：

1. **G0 决策收口**：批准本 ADR 时同步更新总体设计、受影响 ADR 和活动文档索引，不产生两个相互冲突的 active 路线；
2. **G1 停止旧系统测试写入**：记录截止时间，确认没有其他用户和计划内写入；
3. **G2 旧系统离线收口**：完成数据库独立备份和恢复验证，生成 `manual_files` 原地保留清单，登记代码和 migration 状态；不要求制作 `manual_files` 完整副本；
4. **G3 停止旧系统在线服务**：关闭旧前端、后端、定时任务和对外端口，撤销旧应用数据库连接，停止对 `manual_files` 的写入并保留运行说明；共享数据库实例不得随旧应用一并停止；
5. **G4 代码适用性与调用面审计**：区分空仓通用代码、迁移专用代码和旧活动实现，确定正向删除 migration；
6. **G5 开发空库验证**：在新的开发数据库执行完整 migration 链、系统检查和测试，确认最终 schema 不含旧活动表；
7. **G6 最小后端流程**：建立首个账号、组织或课题组、Project和最小Profile，从零创建合规 `DataAsset`；
8. **G7 前端与 API 规划**：基于已验证流程定义用户操作和接口契约，不提前硬编码数据类型；
9. **G8 新仓生产初始化**：使用独立数据库和存储初始化新仓，不导入旧业务数据。

代码部署、数据库初始化、旧系统离线收口和新仓业务验收是独立 Gate。任一开发或测试结果都不能替代生产验收。

## 5. 验收标准

### 5.1 决策验收

- 总体设计和活动索引不再把旧业务数据全量迁移作为目标；
- 旧系统离线收口范围、负责人和数据库恢复门槛明确；
- 所有旧业务数据和关系的不迁移边界无歧义；
- 重新接收与自动迁移的区别有书面定义。

### 5.2 开发空库验收

- 全新数据库能够仅通过版本化 migration 建立；
- migration 最终状态不包含 `Dataset`、`DatasetAccession`、`FileRelation` 等旧活动表；
- 初始化过程不读取旧生产数据库、旧文件清单或网络资源；
- 没有 `Dataset`、Accession、Assembly 或 Annotation 旧记录时，仍能创建合规 `DataAsset`；
- 新资产的文件成员、项目、权限和可选上下文关系能够独立工作；
- 不存在新旧双写、跨库外键或旧关系 fallback；
- 相关系统检查、migration 检查和测试准确记录结果。

### 5.3 旧系统离线收口验收

- 数据库完整备份具有校验记录，并在生产服务器或原磁盘之外保存至少一份副本；
- 数据库隔离恢复演练成功并形成证据；
- `manual_files` 原地存在，已生成相对路径、大小和修改时间清单，已有校验值已登记；
- 已确认旧应用不再写入、重命名或删除 `manual_files`；
- 文档明确说明 `manual_files` 未制作完整备份、不能保证恢复，文件清单不等同于内容备份；
- 数据库、文件清单、代码和 migration 状态具有一致的截止时间；
- 旧前端、后端、定时任务和对外端口已经停止，旧应用不再连接旧数据库；
- 旧数据库能够按恢复说明临时恢复；旧文件只有在原目录仍存在且校验通过时才能重新接收；
- 新仓不依赖旧系统即可运行。

## 6. 后果与风险

### 6.1 正面后果

- 新仓不会继承无法确认的旧关系；
- 不再为一次性迁移持续堆积规则和兼容代码；
- 可以直接验证通用模型是否真正支持空仓和新类型；
- 新旧事实来源和责任边界清晰；
- 避免为约 757G 的旧 `manual_files` 制作一份仅服务于历史系统的完整副本。

### 6.2 代价和风险

- 旧数据不能自动出现在新仓搜索和统计中；
- 用户、项目和必要配置需要按新规则重新建立；
- 使用旧数据需要人工核验和重新接收；
- 旧数据库归档和恢复验证仍具有运维成本；
- `manual_files` 是单份原地源数据，发生误删、覆盖、损坏或存储不可用时无法保证恢复；
- 查询旧元数据需要临时恢复隔离数据库，响应速度低于在线系统。

数据库风险通过明确停止时间、独立备份和恢复演练控制；旧文件风险通过停止写入、清单登记、按需校验和复制导入降低，但不消除。项目接受不制作完整旧文件副本的剩余风险，不通过恢复全量迁移解决。

## 7. 明确不做

本 ADR 不批准：

- 删除旧生产数据库、文件或历史 migration；
- 在数据库备份与恢复验证、文件清单登记和停止写入确认前关闭或删除旧生产系统；
- 创建生产新库或部署新服务；
- 修改现有前端、API、权限或文件访问行为；
- 自动迁移任意旧业务对象或关系；
- 为某种科研数据新增专用核心表；
- 对 openBIS、Kadi4Mat 或其他平台实施 PoC 或迁移；
- 在尚未完成调用审计时删除 T4 或旧系统代码。

## 8. 回滚与停止条件

旧系统停止在线服务前，可以通过暂停后续 Gate 终止实施。旧系统停止后如需核对旧元数据，只能按恢复说明在隔离环境临时恢复旧数据库，不重新开放为活动写入系统；旧文件只从原地保留目录按需核验。

旧系统停止前必须确认旧数据库独立备份和恢复验证成功，并完成 `manual_files` 清单登记和停止写入确认。新仓启用后若验收失败，应停止新数据接收，将已经接收的新仓数据置为只读并另行备份，再回滚应用发布；不得丢弃已接收数据、把数据写回旧系统或临时恢复双写。

遇到以下情况必须停止并请求决策：

- 发现除项目负责人测试之外的用户或关键写入业务；
- 数据库备份或恢复验证失败；
- `manual_files` 清单无法生成，或无法阻止旧应用继续写入；
- 数据库、文件清单、代码和 migration 状态无法形成一致截止时间；
- 新仓必须依赖旧表或旧文件路径才能启动；
- 现有代码无法在不建立第二事实来源的情况下复用；
- 法规、合同或课题要求必须迁移某类历史数据；
- 停止旧系统会导致未预期的业务中断。

## 9. 分阶段待落实事项

以下事项不改变本 ADR 的架构决策，但必须在对应 Gate 前落实：

| 事项 | 最迟完成时间 |
| --- | --- |
| 现有总体设计及 ADR-001 至 ADR-003 的冲突段落、`supersedes` 和活动索引修订 | G0，与本 ADR 正式批准同步完成 |
