# GeneData通用科研数据仓库重新定位说明

> 本文是 GeneData 数据仓库当前 active 总体入口。ADR-004 已批准数据层重新开库、旧系统离线收口和继续基于 GeneData 建设；当前实现状态仍以代码、migration、测试和 CI 为准，本文不授权任何生产操作。

## 一、调整背景

原方案计划在现有 GeneData 中增加 `DataAsset`，并将生产环境已有的 `Dataset`、`DataFile`、文件关系、项目、权限和专业实体尽量转换到新模型中。

生产只读审计表明：

- 现有 `Dataset` 同时承担数据身份、数据类型、文件集合、科研上下文、权限和描述等多种职责；
- 一个 `Dataset` 不一定对应一个真实科研数据资产；
- 部分 transcriptome 和 Hi-C 记录只有元数据描述，没有对应核心文件；
- 历史 `FileRelation` 混合了文件归属、专业上下文和其他业务含义；
- 同一物理文件可能关联多个 Assembly；
- 部分 FASTA 存在多个索引或历史文件；
- 全量自动迁移需要大量猜测，无法保证结果符合真实科研含义。

因此，项目不再以“先修复全部旧数据并完成全量自动转换”为建设前提。重新定位的对象不是单独的 `Dataset`，而是整个科研业务数据层：旧生产数据库和旧文件系统作为历史系统保留，新数据仓库使用独立数据库和独立存储从空仓开始。

## 二、重新定位

新数据仓库确定继续基于 GeneData 建设。GeneData 拟定位为：

> 面向课题组和科研人员的通用科研数据资产管理平台，用统一方式管理真实科研数据、组成文件、科研上下文、权限和来源，并通过 API 支持检索、浏览和外部分析工具。

平台重点回答：

1. 这是什么科研数据？
2. 它由哪些核心文件和辅助文件组成？
3. 它描述哪个样本、组装、注释或其他科研对象？
4. 它属于哪个项目或课题组？
5. 谁可以查看、下载和管理？
6. 它从哪里产生，后续又生成了什么？
7. 外部工具如何在授权条件下使用这些数据？

## 三、与原迁移设想的区别

### 原迁移设想

- 将生产环境现有 `Dataset` 尽量自动转换成 `DataAsset`；
- 尽量保留并修复全部历史文件关系；
- 解决生产数据冲突后再切换；
- 默认接近于 `1 Dataset = 1 DataAsset`。

### 已批准的新定位

- 新数据仓库使用独立数据库和独立文件存储，从零个科研业务记录开始；
- 不迁移旧 `Dataset`、`DataFile` 记录、`FileRelation`、项目、权限、专业实体或它们之间的关系；
- 不把旧文件清单导入新仓业务表，也不建立指向旧主键的外键或跨库业务关系；
- 新数据按照新规则直接登记为 `DataAsset`，并建立新的文件成员、上下文、项目和权限关系；
- 旧生产数据库独立备份并完成恢复验证；旧 `manual_files` 不做完整副本，原地停止写入并登记清单；旧应用随后停止在线服务；
- 以后确实需要使用某份旧数据时，先核验真实文件、科研含义、项目和权限，再作为一份新数据重新接收；
- 重新接收产生新标识和新关系，只在来源记录中保存必要的旧系统引用，不复制旧关系；
- 只有具备真实核心数据载荷的内容才能成为 `DataAsset`，纯描述性元数据不能为了保留数量而强行创建资产；
- 禁止新旧系统长期双写、自动 fallback 或让两套业务数据共同成为新仓事实来源。

“从空仓开始”指新数据库初始没有任何旧科研业务数据和关系，不代表删除、忽略或伪造旧生产数据。旧数据库必须可备份、可恢复并能在隔离环境中临时查询；旧 `manual_files` 只原地保留，不承诺在文件丢失或损坏后可恢复；新仓独立形成新的事实来源。

### 保留通用设计和代码的边界

数据层重新开库不等于重写整个 GeneData。已有实现只有在代码、migration 和测试证明其适用于空仓且不依赖旧业务数据时，才可继续作为新仓基础，例如：

- `DataAsset`、`DataFile` 和 `AssetFileMembership` 的通用职责；
- DataType/Profile 注册表及校验机制；
- 明确的专业上下文关系；
- 通用认证、授权、文件访问、审计和基础服务。

只服务于旧数据识别、候选映射、全量回填、双写或长期兼容的代码不再扩展。是否保留或删除必须先做调用面和测试审计，不得因为路线调整而修改历史 migration 或直接删除仍被使用的实现。

### 新仓目标 schema

空仓不只表示“旧表中没有数据”。新仓最终 schema 不再保留 `Dataset`、`DatasetAccession`、`FileRelation` 等只服务于旧业务体系的活动表和写入入口。

历史 migration 必须保留。实施时先完成模型、命令、API、测试和前端调用面审计，再通过新的正向 migration 删除旧结构。在新的开发数据库从头执行完整 migration 链时，可以经历“创建旧表后再删除旧表”，但最终 schema、当前模型和活动业务入口必须保持一致。稳定运行后是否压缩 migration 历史另行决定，当前阶段不进行 migration squash。

## 四、核心设计原则

### 4.1 固定少量核心实体

系统不能因为新增 genome、annotation、transcriptome、Hi-C、图像或表格等科研类型，就持续增加核心表和后端类型分支。

核心结构应长期保持稳定：

```text
Project
DataAsset
DataFile
AssetFileMembership
DataType
Profile
专业科研上下文关系
权限与审计
```

### 4.2 DataAsset 是统一科研数据身份

`DataAsset` 表示一个能够被管理、授权、检索、引用和使用的真实科研数据资产。

示例：

```text
参考基因组资产
├── genome.fa        core
├── genome.fa.fai    auxiliary
└── Assembly 上下文
```

```text
基因组注释资产
├── annotation.gff3  core
├── statistics.tsv   auxiliary
└── Assembly、Annotation 上下文
```

```text
原始测序数据资产
├── sample_R1.fastq.gz  core
├── sample_R2.fastq.gz  core
└── Sample 上下文
```

### 4.3 DataFile 是物理文件事实来源

`DataFile` 只描述真实物理文件，例如文件标识、名称、大小、校验值、物理状态、发布状态和受控访问位置。

不得再建立平行的物理文件模型。

### 4.4 AssetFileMembership 表达资产组成

`AssetFileMembership` 连接 `DataAsset` 和 `DataFile`，表达：

- 文件属于哪个资产；
- 文件是核心文件还是辅助文件；
- 文件在资产中的专业角色；
- 是否为主文件；
- 文件顺序。

它不承担科研上下文或数据血缘含义。

### 4.5 DataType 与 Profile 负责扩展

`DataType` 表示数据大类，例如：

```text
sequence
feature
raw_reads
matrix
image
table
archive
```

`Profile` 表示具体资产约定，例如：

```text
sequence/reference_genome
feature/genome_annotation
feature/genomic_region_set
raw_reads/paired_end_reads
matrix/contact_matrix
```

Profile 定义元数据字段、必填字段、核心与辅助文件角色、文件数量规则、允许的科研上下文及校验规则。

以后新增或停用科研数据类型，目标上通过受控的 DataType/Profile 治理流程完成，而不是增加数据库表或后端类型分支。由谁配置、如何审批、版本如何发布以及是否需要管理界面，暂不在当前阶段决定；这些规则应在实际登记流程稳定后单独设计。

### 4.6 专业实体是科研上下文

`Sample`、`Accession`、`Assembly` 和 `Annotation` 继续保存专业领域事实，分别回答数据来自哪个样本、对应哪个公共数据库编号、描述哪个组装版本或对应哪套注释。

它们不是 `DataAsset` 的组成文件，也不是平行的数据资产模型。

一个 `DataAsset` 可以选择性关联零个、一个或多个专业上下文。没有 Accession、Assembly 或 Annotation 的数据也必须能够进入仓库。

### 4.7 分离不同维度

必须区分：

- 数据是什么：`DataType + Profile`；
- 数据由什么文件组成：`AssetFileMembership`；
- 数据描述什么对象：专业上下文关系；
- 数据属于哪个项目：`Project`；
- 数据如何产生：独立的数据血缘或分析运行结构。

不能把这些含义全部放进一个类型字段、JSON 字段或通用关系表中。

## 五、旧生产系统离线收口与新仓边界

旧数据和旧关系不再作为新仓建设的前置条件，也不进入新仓初始化过程。

### 5.1 旧系统只做离线收口

旧生产系统需要完成：

1. 数据库制作完整备份和结构备份，在独立存储保存，并完成隔离恢复验证；
2. `manual_files` 原地保留，不制作完整独立副本；生成相对路径、大小和修改时间清单，已有校验值一并登记；
3. 停止旧应用对 `manual_files` 的写入、重命名和删除；
4. 登记当前应用版本、migration 状态和不含密钥的运行说明；
5. 记录数据库、文件清单、代码和 migration 的统一截止时间，关闭旧前端、后端、定时任务和对外端口；
6. 登记数据库备份位置和保留期限，以及 `manual_files` 的保管位置、负责人和访问权限。

项目负责人确认旧系统没有其他用户，只有本人测试，因此无需设置长期在线只读观察期。`manual_files` 清单是观察记录，不是文件内容备份；实际重新接收时再计算并核验源文件校验值。由于不保存完整副本，文件被误删、覆盖、损坏或所在存储不可用时可能无法恢复，项目明确接受这一风险。旧数据库恢复成功也不代表旧文件内容可恢复。

数据库、文件清单、代码版本和 migration 状态必须对应明确的停止写入截止时间。完成数据库恢复验证、文件清单登记和停止写入确认前，不得删除旧数据库、旧文件或旧应用版本。旧关系语义不清、类型混乱和归属冲突不再为迁移目的持续修复。

文件清单和运行登记属于运维证据，不导入新仓的业务表。

### 5.2 新仓独立运行与初始化

新仓必须使用独立数据库和独立文件目录。初始科研业务内容为空，初始化内容分为四类：

1. **migration 创建的结构**：DataAsset、DataFile、AssetFileMembership、Project、专业上下文关系、用户权限和 Django 系统表；
2. **受版本控制的系统配置**：经过确认的最小 DataType/Profile、文件角色、metadata schema、状态和权限规则；
3. **部署配置**：数据库连接、文件存储根目录、密钥、域名、日志和备份位置，通过环境或部署系统提供，不提交到 Git；
4. **人工创建的首批业务记录**：首个系统管理账号、数据治理角色、首个组织或课题组、首个 Project 和第一份验证用 DataAsset。

真实用户、项目和科研数据不通过 schema migration 自动创建。初始化工具如确有必要，必须小型、幂等、可审计，并复用唯一业务 service，不形成第二套写入规则。

新仓不得：

- 直接写入旧数据库或旧文件目录；
- 把 `manual_files` 中的路径直接登记为活动 `DataFile` 的存储位置；
- 通过符号链接、硬链接或目录映射直接使用旧文件；
- 复用旧业务表主键作为新仓身份；
- 建立跨库外键；
- 自动复制旧项目、用户业务关系、权限或专业上下文；
- 通过兼容代码在旧关系缺失时自动 fallback。

首个账号、数据治理角色、基础组织和 Project 的具体创建步骤必须在最小后端流程验证前形成可执行清单；不得以“方便登录”为由顺带迁移任何旧业务关系。

### 5.3 旧数据只允许重新接收

未来确实需要使用旧数据时，按新数据准入流程重新接收：

1. 从 `manual_files` 清单定位原地保留的真实文件；确需旧元数据时，才临时恢复旧数据库；
2. 计算并核验源文件校验值、内容和可访问性；
3. 重新确认数据类型、Profile、核心与辅助文件；
4. 重新确认项目、权限和必要科研上下文；
5. 将文件复制到新仓独立存储，不直接引用、链接或移动旧文件；
6. 重新计算目标文件校验值并确认与源文件一致；
7. 创建新的 `DataFile`、`DataAsset` 和新关系；
8. 保存最小来源说明和旧系统相对引用，便于审计；公开接口不暴露旧服务器绝对路径。

只有源文件仍存在且校验通过时才能重新接收。该过程不是关系迁移，不得批量导入旧文件、复制旧关系或形成持续同步。

已有 T0、T1 和 T4 生产只读审计作为“旧业务数据不适合自动迁移”的决策证据归档，不再要求逐条解决候选冲突。原 T4 全量回填准备、T5 一致性切换和 T6 迁移后退役路线已经终止，由“旧系统离线收口、新仓空库启用”替代。

## 六、面向人群

### 6.1 普通科研人员

- 上传或登记科研数据；
- 按项目、样本、组装、注释和数据类型查找数据；
- 查看资产由哪些文件组成；
- 下载授权范围内的文件；
- 将数据交给 JBrowse、脚本或外部分析工具使用。

普通科研人员不需要理解数据库表和内部关系模型。

### 6.2 课题组负责人和项目负责人

- 查看本课题组的数据资产；
- 管理成员访问权限；
- 确认数据是否可以公开；
- 查看数据完整性和使用情况；
- 确认重要数据是否已经登记和保存。

### 6.3 数据治理人员

数据治理人员不等于数据库管理员或系统超级管理员。具体角色、审批流程和管理界面将在后续阶段决定。

- 创建、批准、停用和归档 Profile；
- 管理词表和文件角色；
- 审核新资产登记；
- 处理数据冲突；
- 管理项目级权限；
- 查看审计记录；
- 在不修改后端代码的情况下增加新数据类型。

已发布或已经被 DataAsset 引用的 Profile 不得物理删除；只有从未发布、从未被引用的草稿 Profile 才允许删除。

### 6.4 平台运维人员

- 管理存储、数据库、备份和恢复；
- 监控文件完整性；
- 管理系统升级；
- 保证权限和文件访问安全；
- 不参与日常科研类型配置。

### 6.5 外部工具和开发人员

- 通过稳定 API 查询资产、文件和上下文；
- 在授权后读取文件；
- 将 JBrowse、分析脚本、工作流和计算平台连接到数据仓库；
- 保存输入文件、输出文件、参数、软件版本和运行记录；
- 不依赖服务器绝对路径。

## 七、非核心范围

当前数据仓库不以以下能力为首要目标：

- 完整电子实验记录本；
- 实验室设备管理；
- 采购和试剂库存；
- 通用计算任务调度平台；
- 面向公众的论文数据发布仓库；
- 为每种科研类型开发专用后端模型；
- 自动推断并修复全部历史数据关系。

这些能力以后可以通过外部系统、插件或 API 集成，但不能使核心数据模型持续膨胀。

## 八、实现路线

新数据仓库确定继续基于 GeneData 建设，复用经空库验证仍然合理的通用模型、服务、权限、文件访问和基础组件。openBIS、Kadi4Mat 和 FAIRDOM-SEEK 可作为设计参考，但不再是本阶段的平台选型候选，也不阻塞 GeneData 空仓实施。

继续使用 GeneData 不代表保留全部旧实现。新仓必须通过空数据库 migration、最小后端流程和针对性测试证明：

- 新增数据类型原则上不需要修改核心 model 或增加类型分支；
- Profile 能表达文件、元数据和科研上下文规则；
- DataAsset、DataFile 和专业上下文能够在没有旧数据时独立工作；
- 权限和文件访问安全失败；
- 新仓不依赖旧数据库、旧文件路径或旧业务接口。

## 九、前端影响与当前边界

本次重新定位会影响未来前端的信息架构和操作流程，但当前阶段不修改前端代码、不设计具体页面，也不批准新 API。

当前只固定以下边界：

- 新前端最终以 `DataAsset` 为科研数据身份，不依赖旧 `Dataset` 业务关系；
- 后端设计不能假设旧前端永远不变；
- 旧系统停止在线服务后只作为离线档案存在；未来新前端不得通过双写、跨库查询或 fallback 混用旧关系；
- 在正式定义新 API 之前，另行梳理创建、检索、文件成员、科研上下文、权限和 Profile 配置等用户流程；
- 页面结构、视觉样式、组件和具体路由推迟到数据模型、空库启动和最小后端流程验证之后。

## 十、后续讨论约束

后续方案不得再默认：

- 必须迁移任何旧科研业务数据或关系；
- 一个 `Dataset` 对应一个 `DataAsset`；
- 必须先解决全部生产历史问题；
- 每种科研数据都需要建立专用表；
- 旧系统必须长期在线才能查询历史数据。

后续评审必须区分：

- 已有事实；
- 当前已批准设计；
- 本文提出但尚未批准的定位调整；
- 尚待 PoC 验证的假设；
- 正式生产实施状态。

## 十一、决策状态与分阶段落实

ADR-004 已批准：

1. 终止全部旧科研业务数据和关系的迁移，而不只是取消 `Dataset` 回填；
2. 新仓继续基于 GeneData，使用独立数据库和独立文件存储从空业务库启用；
3. 旧数据库独立备份并恢复验证；旧 `manual_files` 原地停止写入并登记清单，不制作完整副本且不保证恢复；旧应用随后停止在线服务；
4. 旧数据只能按新规则重新接收；
5. 保留适合空仓的通用设计和代码，停止扩展迁移专用实现；
6. 原 T4 全量回填准备、T5 一致性切换和 T6 迁移后退役路线终止；
7. 前端能力规划在开发空库和最小后端流程验证后开始。

旧数据库备份介质、`manual_files` 清单与停止写入措施、停止日期、代码删除清单、初始化步骤、前端/API 规划和生产新仓初始化仍按 ADR-004 的 Gate 分别落实。任何后续阶段都不得从本文推断为已经完成。
